Web Components sin manifest
o con un manifest custom

hanko vive en el contrato. ¿Qué ocurre cuando el contrato no existe, o existe pero habla otro idioma? Este report disecciona los dos casos límite y propone cómo debe comportarse el motor sin traicionar su tesis de confianza.

Alcance de este documento

Esto NO forma parte del planning del núcleo de hanko. El camino principal —fases F0–F7 y ADR-001— asume que el componente trae un CEM (o un manifest normalizable a CEM). Este documento trata los componentes que se salen de ese supuesto: sin manifest o con un formato custom no estándar. Es un caso especial deliberadamente separado, documentado aquí para no contaminar el camino feliz y para tener una decisión lista cuando toque abordarlo. Decisión aún abierta; lo que sigue es la propuesta, no la resolución cerrada.

00Todo se reduce a una sola pregunta

Ambos casos —sin manifest y con manifest ajeno— son la misma pregunta vista desde dos ángulos:

La lente

¿Tiene hanko un contrato independiente y declarado contra el que verificar la implementación?

Esto importa porque la tesis de hanko es: el humano revisa el contrato (pequeño); hanko verifica que la implementación lo honra (grande). Si no hay contrato, no hay nada que honrar — y el motor pierde su razón de ser, no por incapacidad técnica, sino porque la conformidad necesita dos partes que comparar.

Manifest customSíOtro dialectoAdaptar → CEM en el borde

AWeb Component sin manifest alguno

Existe un Custom Element registrado con customElements.define('mi-comp', …), vive en el DOM, pero no trae CEM. La entrada principal de hanko falta. ¿Qué se puede hacer?

Qué pierde hanko inmediatamente

Sin contrato declarado, desaparecen de golpe las dos capas más valiosas:

✗ Validación de contrato — no hay props/eventos/slots declarados que comprobar.

✗ Detección de drift — no hay un "lo prometido" del que la implementación pueda desviarse.

✓ Sobreviven las pruebas universales que no dependen de un contrato: a11y (axe, foco, teclado, ARIA) y resiliencia (no peta con props basura, SSR, RTL). Son expectativas que aplican a cualquier componente, declare lo que declare.

Es decir: hanko degrada de verificador-de-conformidad a sonda-de-comportamiento. Puede decir "este componente no se rompe y es accesible", pero no "este componente cumple lo que promete" — porque no promete nada.

Qué se puede inferir interrogando el runtime

Se podría reconstruir un contrato mínimo introspeccionando el elemento vivo. Pero la recuperación es desigual y, sobre todo, conductual — hay que manipular el elemento y observar, no leer una declaración:

const Ctor = customElements.get('mi-comp');
const attrs = Ctor?.observedAttributes ?? [];   // ['size','disabled'] — solo los observados

// Slots/parts solo aparecen tras renderizar e inspeccionar el shadowRoot.

A.2 · La trampa: un contrato inferido es circular

El defecto fatal de la inferencia

Si el contrato lo derivas de la implementación, ya no puedes "verificar que la implementación honra el contrato" — porque el contrato es la implementación. Es un razonamiento circular y autocumplido: por definición coinciden. Un contrato inferido nunca detecta drift, porque no existe nada independiente de lo que desviarse.

Esta es la diferencia profunda entre un manifest declarado por un humano (intención, independiente del código) y uno inferido del runtime (eco del código). Solo el primero genera confianza real; el segundo solo confirma que el componente es consistente consigo mismo — útil, pero no es un sello de confianza.

Las tres salidas posibles

a) Rechazo

Exigir CEM como condición de entrada. Limpio y honesto, pero excluye a muchísimos componentes reales (gran parte de las librerías no envían CEM).

Estricto · poca adopción

b) Inferencia runtime

Derivar un contrato del DOM vivo. Recupera poco y es circular para drift. Sirve para onboarding, no para sellar confianza por sí solo.

Útil como borrador, no como sello

c) Híbrido (recomendado)

Aceptar, correr solo las pruebas universales (a11y/resiliencia) y emitir un sello degradado y etiquetado "sin manifest declarado". Nunca al nivel de un CEM real.

Adopción + honestidad

BManifest en formato custom / no estándar

Aquí sí hay contrato —el componente se describe a sí mismo— pero no en CEM. Existen muchos dialectos reales en la naturaleza:

La respuesta arquitectónica: adapter en el borde de ingestión

La regla es la misma que ya rige el core de hanko (el core nunca importa de shibui; recibe config + manifest): el core habla un único idioma, CEM, y todo lo ajeno se normaliza en la frontera. Cada formato extranjero pasa por un adapter que emite CEM (posiblemente parcial):

// El core nunca conoce formatos ajenos. Solo el borde traduce.
interface ManifestAdapter {
  detect(input: unknown): boolean;        // ¿es mi formato?
  toCEM(input: unknown): CEMResult;      // → CEM + reporte de cobertura
}

interface CEMResult {
  manifest: CustomElementsManifest;   // lo que SÍ se pudo traducir
  coverage: { mapped: string[]; dropped: string[] };  // honestidad sobre la pérdida
}

// hanko core recibe SIEMPRE CEM, venga de donde venga.

Esto encaja de forma natural con la regla de oro del ADR-001 (ausencia ≠ incumplimiento): si un adapter solo recupera props pero no eventos, emite un CEM con props y sin eventos → hanko valida props y omite eventos. La misma maquinaria, sin código especial.

La preocupación real: traducción con pérdida

Un formato ajeno puede codificar cosas que CEM no expresa, o al revés. El adapter debe reportar su cobertura (mapped / dropped), porque eso alimenta la cobertura del sello: el Trust Report dirá "validado a partir de web-types: se mapearon atributos y slots; se descartaron tipos de unión que el formato no expresa".

★Modelo de ingestión en tres niveles

Los dos casos colapsan en un único embudo de entrada. CEM es el lingua franca interno; lo demás se resuelve en el borde o cae a sondeo:

① y ② confluyen en el mismo core y obtienen sello pleno (② con su cobertura anotada). ③ se desvía a un carril aparte: nunca toca la validación de contrato y solo puede aspirar a un sello degradado.

!Salvaguarda: el sello debe declarar su procedencia

El riesgo más serio no es técnico: es de integridad. Un sello derivado de un contrato inferido o de una traducción con pérdida no puede parecer tan fuerte como uno nacido de un CEM declarado por un humano. Si todos los sellos se ven iguales, hanko miente.

Regla de honestidad

Todo Trust Report declara la procedencia y la cobertura del contrato: "sello basado en CEM nativo" · "adaptado de web-types (sin tipos)" · "inferido del runtime — sin conformidad". La confianza exige transparencia sobre de dónde salió el contrato, no solo si se cumplió.

ProcedenciaDrift detectableNivel de sello
CEM declarado (humano)SíPleno
Adaptado de formato customParcial (según cobertura)Pleno con asteriscos
Inferido del runtimeNo (circular)Degradado / smoke

↻El giro constructivo: bootstrap de CEM

La debilidad del caso "sin manifest" se convierte en una función de onboarding. hanko puede inferir un borrador de CEM del runtime y proponérselo al humano para que lo ratifique y corrija. En cuanto un humano lo bendice, ese borrador deja de ser un eco del código y pasa a ser un contrato independiente.

Tras la ratificación, la detección de drift vuelve a funcionar, porque ya existe algo independiente de lo que desviarse. Convertiste un componente opaco en uno gobernado — sin pedirle al autor que escriba el CEM desde cero.

✓Decisión propuesta (para ADR futuro)

1. CEM es el único idioma del core. Nada ajeno lo cruza sin normalizar.

2. Formatos custom → adapters en el borde, que emiten CEM + reporte de cobertura (mapped/dropped). Encaja con ausencia ≠ incumplimiento sin código especial.

3. Sin manifest → carril degradado: solo pruebas universales (a11y/resiliencia), jamás sello de conformidad. La inferencia es circular y no detecta drift.

4. Bootstrap opcional: ofrecer borrador inferido para que un humano lo ratifique y lo promueva a CEM real. Onboarding, no atajo.

5. Honestidad obligatoria: el Trust Report siempre declara procedencia y cobertura. Tres orígenes ⇒ tres fuerzas de sello distintas y visibles.

En una frase

hanko acepta a todos, pero no sella a todos por igual: traduce lo que puede, sondea lo que no, y nunca disfraza un eco del código de contrato verificado. La confianza no se finge — se procedencia.
