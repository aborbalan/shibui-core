Del sello al trabajo → issues de GitHub

hanko ya dice qué componentes no pasan el sello de confianza. Esta fase cierra el bucle: convierte esos hallazgos en issues de GitHub accionables — pero solo cuando se lo pides. Es opt-in de extremo a extremo: nada se crea en un push normal.

⚐ opt-in · no default idempotente · re-correr no duplica cero deps · fetch global 1 issue / componente sin sello solo violations · warnings no

El flujo, de punta a punta

El Trust Report sigue intacto y puro. El emisor es una capa encima del trust-report.json que report ya deja en disco — no recalcula nada, no toca los checks, no importa shibui.

Por qué nunca se dispara solo

Dos pestillos independientes. Hay que abrir el que corresponda a propósito.

Pestillo 1 · pipeline

El script issues está fuera del camino por defecto

Ni report ni report:full lo invocan. Para que pase algo hay que llamar pnpm --filter @shibui-ui/hanko issues explícitamente.

Pestillo 2 · CI

El step de CI está gateado por un flag manual

El step vive en ci-lib.yml con if: inputs.github_issues == 'true'. Solo se pone a true lanzando el orchestrator a mano con force_hanko_issues (workflow_dispatch). El deploy de cada main no crea issues.

Idempotencia: el marcador es la clave

Cada issue lleva un comentario HTML invisible <!-- hanko:component=<tag> --> en el cuerpo. La sincronización casa los issues por ese marcador (no por título), así que re-correrla converge en vez de duplicar.

Anatomía de un issue generado

Un componente con dos capas en rojo se traduce así:

[hanko] lib-stepper — 2 violaciones de confianza hanko hanko:contract hanko:resilience
<!-- hanko:component=lib-stepper -->  ←  clave de dedupe · no editar
判 lib-stepper no pasa el sello de confianza
Capas que fallan: contract · resilience
  • contract/method: método declarado "next" ausente en el elemento
  • resilience/empty: el componente se rompió al montar vacío (steps.map is not a function)

Trust Report completo: hanko-report.web.app · Issue generado por hanko, se cierra solo al volver a sellar.

Cómo se usa

Local (CLI)

# 1· genera el report
pnpm --filter @shibui-ui/hanko report

# 2· ensayo SIN red (imprime el plan)
pnpm --filter @shibui-ui/hanko issues --dry-run

# 3· crea/actualiza/cierra de verdad
GITHUB_REPOSITORY=owner/name \
GITHUB_TOKEN=*** \
  pnpm --filter @shibui-ui/hanko issues

CI (manual)

# GitHub → Actions → Orchestrator
# → Run workflow
  branch: main
  force_hanko_issues: ☑ true

# orchestrator → ci-lib:
#   github_issues = 'true'
# job deploy-hanko-report:
#   permissions: issues: write
#   step (if github_issues) → issues

Limitaciones conocidas (v0)

⚠ decisiones de política, documentadas a propósito
  • updateIssue reescribe el set de labels. Una label puesta a mano (p.ej. priority:high) se pierde en la siguiente sync. hanko «posee» estos issues; si hace falta triaje persistente, omitir labels en el update.
  • Solo se listan issues abiertos. Un issue cerrado a mano (wontfix) de un componente que sigue sin sello se recreará. Para respetar el cierre manual habría que listar también cerrados.
  • El gate duro sigue pendiente. Esta fase reporta y crea trabajo; aún no falla el build cuando un componente no cumple su nivel exigido (eso es el resto de F6).
