El check de contrato

F0–F2 son estáticos: leen el manifest. F3 es la primera capa que mira el runtime. Su trabajo es comparar lo que un componente declara con lo que su elemento vivo expone, y estampar la diferencia. Aquí está el mecanismo, pieza a pieza.

01 · la idea

Dos retratos del mismo componente

hanko enfrenta dos descripciones del mismo elemento y busca dónde divergen. Una viene del papel (el manifest); la otra, de la realidad (el DOM). contractCheck() las cruza y emite un veredicto.

declarado

ComponentContract

← ingestCem() sobre el CEM

  • propiedades + tipos
  • atributos + reflects
  • métodos · eventos · slots
⇄
observado

ComponentRuntime

← un harness monta el elemento

  • registered (¿definido?)
  • props · observedAttributes
  • métodos · reflexión real
ComponentContract + ComponentRuntime → contractCheck() → ContractResult
02 · arquitectura

El motor no toca el DOM

Principio innegociable de hanko: el core nunca importa @shibui-ui/ui ni monta navegadores. Por eso F3 parte en dos. ComponentRuntime es el límite de abstracción: una instantánea de hechos observados. Quién la rellena —un harness del consumidor o el probe DOM genérico con @vitest/browser— es problema de otra capa.

cerebro · incremento 1

contractCheck() — puro

Compara declarado ↔ observado. Sin DOM, sin navegador, sin shibui. Se testea en Node con observaciones falsas. Esto es lo que se entrega hoy.

músculo · incremento 2

harness de runtime

Monta cada elemento, lee su prototipo y prueba la reflexión para construir el ComponentRuntime real. Genérico y parametrizado: no conoce shibui.

03 · la regla de oro

Ausencia ≠ incumplimiento — en ambos sentidos

hanko solo valida lo que puede afirmar. Si el manifest no lo declara, o el harness no lo observó, la faceta se omite (y queda registrada en skipped). Solo lo declarado que el runtime contradice es violación. El sello declara siempre su cobertura: checked dice qué se comprobó de verdad.

SituaciónVeredicto de hanko
El manifest no declara la facetaomitir · no es fallo
El harness no observó la facetaomitir · no es fallo
Declarado y el runtime coincideconforme
Declarado y el runtime lo contradiceviolación
04 · qué comprueba

Las facetas del contrato

Cinco verificaciones en el incremento 1. La registrabilidad es el suelo: sin ella no hay elemento que inspeccionar y el resto se omite.

facet · registration

¿está registrado?

customElements.get(tag) debe estar definido. Si no, nada más se puede mirar.

runtime del Floor (de F2)
facet · property

props declaradas

Cada propiedad del manifest debe existir en la instancia del elemento.

facet · attribute

atributos mapeados

Cada prop con attribute debe figurar en observedAttributes.

facet · reflect

reflexión real

Una prop con reflects:true debe reflejar de verdad — solo si el harness lo probó.

facet · method

métodos declarados

Cada método del manifest debe existir como función en el elemento.

próximo incremento

eventos · slots

Modelados, pero su verificación necesita ejercitar y renderizar el elemento. Llegan después.

05 · exigencia

Dos niveles

El mismo motor, dos varas de medir. La diferencia es qué hace con lo que el manifest no declara.

por defecto

conformance

Lo declarado existe y coincide en runtime. Un vanilla parco pasa validando solo lo poco que declara; un Lit rico se gana una validación más estricta por declarar más.

opt-in

strict

Además, el runtime no debe exponer API pública no declarada. Una prop pública sin declarar pasa a ser violación: convierte la ausencia en fallo para quien busca el sello alto.

06 · el resultado

Un sello de ejemplo

Así se ve un ContractResult: el componente declaró un método que el elemento no tiene (violación), no se probó la reflexión y no se declararon eventos (ambos omitidos).

contractCheck(libCard, runtime) ⟶ {
  tagName: 'lib-card', level: 'conformance', pass: false,
  violations: [
    { facet: 'method', member: 'expand', message: 'método declarado "expand" ausente en el elemento' }
  ],
  checked: { registration: true, properties: 3, attributes: 2, methods: 1, reflect: 0 },
  skipped: [ 'reflect (el harness no probó…)', 'events / slots (no declarados)' ]
}
判

Estado: esto es el incremento 1 de F3 — el motor de conformidad, puro y testeado en Node. Vive en src/checks/contract.ts + src/core/runtime.ts, en la rama feature/hanko-contract. El incremento 2 añade el harness @vitest/browser que observa los elementos vivos de shibui-ui y corre el check sobre los 102 componentes reales.
