El runner y cómo se comunican
hanko ↔ shibui-ui

La idea central, primero: las dos librerías no se comunican por código. Se comunican por un artefacto — el manifest. hanko nunca importa shibui; lee un JSON.

01La idea central: comunican por artefacto, no por código

Lo intuitivo sería pensar que hanko import-a shibui-ui y lo inspecciona. No. Eso acoplaría hanko a shibui y rompería su principio de ser genérico. En su lugar:

El contrato es el canal

shibui-ui produce un Custom Elements Manifest (custom-elements.json) como artefacto de build. hanko lee ese fichero. Eso es todo lo que cruza entre ambas. Ni un import, ni una dependencia npm de hanko → shibui.

hanko depende del formato CEM (un estándar público), no de shibui. Por eso el mismo runner serviría para cualquier librería de Web Components que emita un CEM.

02El flujo completo

Fíjate en la frontera punteada: lo único que la cruza es el custom-elements.json. Todo lo de la derecha (ingestión, Floor, sello) vive dentro de hanko y no sabe nada de Lit ni de shibui.

03Qué hace el runner, paso a paso

  1. Localiza el manifest. Una ruta a custom-elements.json (en el monorepo: packages/shibui-ui/dist/custom-elements.json, que produce cem analyze).
  2. Lee y parsea. readFileSync + JSON.parse → un objeto CEM en memoria.
  3. Ingesta. ingestCem(manifest) normaliza el CEM al modelo interno (ContractSet).
  4. Sella. smoke(manifest) aplica el Floor a cada componente y calcula su cobertura.
  5. Reporta. Imprime el SmokeReport (resumen + sello por componente). En F6 también JSON/HTML.
Es tooling, no runtime

El runner es un script de dev/CI que ejecutas con pnpm. No es una dependencia que importes en tus componentes. shibui no "llama" a hanko: hanko se ejecuta sobre el output de shibui.

04El código (incremento 2 de F2)

El runner es delgadísimo — toda la lógica ya vive en smoke(). Solo añade I/O:

// src/smoke/run.ts
import { readFileSync } from 'node:fs';
import { smoke } from './smoke';

const path = process.argv[2] ?? '../shibui-ui/dist/custom-elements.json';
const manifest = JSON.parse(readFileSync(path, 'utf-8'));

const report = smoke(manifest);   // ← toda la lógica, agnóstica de shibui

console.log(`hanko smoke · Floor`);
console.log(`  total ${report.total} · pass ${report.passed} · fail ${report.failed}`);
for (const s of report.seals) {
  const mark = s.pass ? '✓' : '✗';
  console.log(`  ${mark} ${s.tagName}`);
}

Y se invoca como herramienta de workspace:

# package.json de hanko: "smoke": "tsx src/smoke/run.ts"
pnpm --filter @shibui-ui/hanko smoke
# o apuntando a otro CEM cualquiera:
pnpm --filter @shibui-ui/hanko smoke ./ruta/a/custom-elements.json

Necesita @types/node + un runner de TS (tsx), por eso es un incremento aparte del núcleo puro ya implementado.

Valor desde el minuto uno

Aunque el Floor sea mínimo, la cobertura (qué declara cada componente) te da ya un mapa accionable: qué componentes tienen manifest rico vs pobre, dónde faltan eventos/slots declarados, etc. Eso es información útil sobre tus 99 componentes antes de tener verificación profunda (F3).

06Dos canales de comunicación (ahora y después)

CanalQué cruzaPara quéFase
Estático (fichero)custom-elements.jsonLeer el contrato declarado: Floor, contrato, coberturaF2 (ahora)
Runtime (DOM)El elemento vivo renderizadoVerificar declarado ↔ real (drift), a11y, resilienciaF3+ (futuro)

El runner de F2 usa solo el canal estático — ni navegador ni DOM, pura lectura de JSON. En F3, hanko añadirá un segundo canal: cargar los componentes en un navegador de test (@vitest/browser) para comparar lo que el manifest promete con lo que el elemento hace. Pero eso es otro canal, aditivo; no cambia el primero.

07Por qué desacoplado por el manifest

1. Genericidad. El core de hanko nunca importa shibui. Si mañana quieres verificar otra librería de Web Components, solo necesitas su CEM. hanko no cambia.

2. Sin acoplamiento de versiones. hanko no depende de la versión de shibui ni de su build. Depende del formato CEM (estándar estable).

3. El contrato es revisable por humanos. El manifest es pequeño y legible; un humano lo revisa, hanko verifica que la implementación lo honra. Justo la tesis del producto.

4. Es la misma costura de los adapters. El borde donde el runner lee el CEM es donde, en el futuro, enchufarán los adapters de formatos custom (caso especial). Un solo punto de entrada.

En una frase

shibui emite un manifest; hanko lo lee. Esa es toda la conversación entre ambas — un fichero JSON cruzando una frontera, sin que ninguna conozca el código de la otra.
