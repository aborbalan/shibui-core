01Web Components nativos: la plataforma cruda

“Web Components” no es una librería, es un conjunto de APIs estándar del navegador. No hay nada que instalar. Se apoyan en tres piezas que encajan entre sí:

① Custom Elements — registrar una etiqueta HTML propia (<lib-button>) asociada a una clase que extiende HTMLElement.

② Shadow DOM — un árbol DOM encapsulado y aislado, con sus estilos scopeados que no se filtran ni reciben fugas del exterior.

③ Templates & Slots — <template> para markup inerte reutilizable y <slot> para proyectar contenido del usuario dentro del shadow tree.

Un componente nativo mínimo se ve así — y aquí está el punto: tú gestionas todo a mano.

class LibButton extends HTMLElement {
  // 1. Declaras qué atributos observar
  static get observedAttributes() { return ['variant', 'disabled']; }

  constructor() {
    super();
    this.attachShadow({ mode: 'open' }); // crea el shadow root
  }

  // 2. Lifecycle: se llama al insertarse en el DOM
  connectedCallback() { this.render(); }

  // 3. Reaccionas a CADA cambio de atributo, manualmente
  attributeChangedCallback(name, oldVal, newVal) { this.render(); }

  // 4. Re-pintas el HTML completo a string — sin diffing
  render() {
    const variant = this.getAttribute('variant') ?? 'solid';
    this.shadowRoot.innerHTML = `
      <style>button { /* ... */ }</style>
      <button class="${variant}"><slot></slot></button>
    `;
  }
}
customElements.define('lib-button', LibButton);

El ciclo de vida que te da el navegador

  1. constructor() — se crea la instancia. Aquí montas el shadow root.
  2. connectedCallback() — el elemento entra en el DOM. Primer render.
  3. attributeChangedCallback() — cambia un atributo observado. Tú decides qué re-renderizar.
  4. disconnectedCallback() — sale del DOM. Limpieza manual de listeners.
El dolor real

Nativo funciona, pero te deja resolviendo a mano lo tedioso: reactividad (re-pintar string completo en cada cambio, sin diff eficiente), el desfase atributo ⇄ propiedad (un disabled string vs un boolean JS), y plantillas como template strings sin tipado ni escapado. A escala, eso es mucho boilerplate repetido y propenso a errores.

02Lit: una capa fina sobre el estándar

Lit no reemplaza los Web Components — los potencia. Sigues produciendo un Custom Element estándar con Shadow DOM; Lit (~5 KB) solo elimina el boilerplate y añade reactividad eficiente. Su clase base LitElement extiende HTMLElement.

El mismo botón, en Lit — y exactamente así es como está escrito lib-button en shibui-ui:

import { LitElement, html, css } from 'lit';
import { customElement, property } from 'lit/decorators.js';

@customElement('lib-button')              // registra la etiqueta por ti
export class LibButton extends LitElement {

  @property({ type: String, reflect: true })   // propiedad reactiva + refleja a atributo
  variant = 'solid';

  @property({ type: Boolean, reflect: true })
  disabled = false;

  static styles = css`button { /* scopeado al shadow */ }`;

  // render() declarativo. Lit hace el diff: solo toca lo que cambió.
  render() {
    return html`<button class=${this.variant} ?disabled=${this.disabled}>
              <slot></slot>
            </button>`;
  }
}

Qué te regala Lit respecto al nativo

Reactividad automática

  • Cambias this.variant y el re-render se programa solo.
  • lit-html hace diffing: actualiza solo los nodos afectados, no todo el innerHTML.
  • Batch asíncrono: varios cambios → un único render.

Plantillas declarativas

  • html`…` con interpolación segura (auto-escapado).
  • Bindings expresivos: ?attr (booleano), .prop, @event.
  • Sin innerHTML manual ni concatenar strings.

Atributo ⇄ propiedad resuelto

  • reflect: true sincroniza la propiedad JS con el atributo HTML.
  • Conversión de tipos (Boolean, Number…) gestionada.
  • Es justo lo que shibui usa para que variant sea estilizable por CSS.

Ergonomía + metadatos

  • Decoradores (@customElement, @property) = menos ruido.
  • Esos decoradores son código declarativo legible por herramientas → clave para el manifest.
  • Estilos co-localizados con css`…`.
Idea central

La salida de un componente Lit es un Web Component estándar. Cualquiera puede usar <lib-button> en React, Angular, Svelte o HTML plano sin saber que dentro hay Lit. Lit es build-time / authoring-time; el runtime es la plataforma.

La última fila es la bisagra hacia la siguiente sección: porque Lit declara las props con @property y los eventos/slots con JSDoc, una herramienta puede leer ese código y extraer un mapa completo del componente. Eso es el manifest.

04El Manifest: el contrato legible por máquinas

Un componente sabe describirse a sí mismo en el código (su tag, sus props, sus tipos, sus eventos, sus slots), pero ese conocimiento está atrapado dentro de la clase. El Custom Elements Manifest (CEM) lo extrae a un fichero custom-elements.json — un JSON estándar que describe cada componente de la librería de forma neutral.

Lo genera cem analyze, que parsea el código fuente —los decoradores @property, los tipos TypeScript, los comentarios @fires / @csspart— y emite algo así:

{
  "schemaVersion": "1.0.0",
  "modules": [{
    "path": "src/components/atoms/button/lib-button.component.ts",
    "declarations": [{
      "kind": "class",
      "customElement": true,
      "tagName": "lib-button",
      "members": [
        { "name": "variant", "attribute": "variant",
          "type": { "text": "'solid' | 'outlined' | 'ghost'" }, "default": "'solid'" },
        { "name": "disabled", "type": { "text": "boolean" }, "default": "false" }
      ],
      "events": [{ "name": "ui-lib-click" }],
      "slots":  [{ "name": "", "description": "Contenido del botón" }]
    }]
  }]
}

La relación, en una frase

Manifest ⇄ Web Components

El código del componente es la fuente de verdad; el manifest es su reflejo serializado y neutral. Lit hace que ese reflejo sea fácil de generar (props declarativas), y el manifest hace que todo lo que rodea al componente —docs, IDE, wrappers, tests— se derive de un único origen en vez de duplicarse a mano.

Por qué importa: una fuente, muchos consumidores

Sin manifest, cada uno de esos consumidores tendría que volver a describir el componente a mano y mantenerlo sincronizado. Con manifest, se generan y el drift (desincronización) se detecta en CI.

05Cómo lo usa shibui-ecosystem (tu caso real)

Esto no es teoría aquí: es exactamente la arquitectura de @shibui/ui. El manifest CEM es el eje del tooling, y generate-components-api.ts lo dice literalmente en su cabecera: “fuente de verdad = el código”.

API de componentes

  • generate-components-api.ts lee dist/custom-elements.json.
  • Emite components.generated.ts para shibui-api (NestJS).
  • Fusiona un overlay editorial (status, version, tags).
  • Salida determinista → git diff --exit-code como drift-guard.

Wrappers & tipos

  • generate-wrappers.ts y los mappers/ derivan React/Angular/Svelte.
  • Cada framework consume el mismo manifest, sin reescribir props.

Conformidad de props

  • props-conformance.test.ts y manifest-cohesion.test.ts validan que código, CSS y manifest no divergen.
  • Es tu Cohesión de props Nivel 2 (orphan-check / reflect) en ci-lib.

hanko (a futuro)

  • Tu motor de confianza es manifest-driven por diseño.
  • Verifica Web Components contra su manifest declarado → el manifest pasa de documentación a contrato verificable.
El círculo se cierra

Lit hace que tus componentes sean fáciles de describir → el CEM los describe en JSON neutral → tu tooling y hanko los consumen y verifican. El manifest es lo que convierte una colección de Web Components en un sistema gobernado por un único contrato.

Resumen en tres líneas:

› Web Components son el estándar del navegador: potentes pero crudos.

› Lit es una capa fina que les añade reactividad y ergonomía sin dejar de producir el estándar.

› El Manifest serializa esos componentes a un contrato neutral del que se deriva —y contra el que se verifica— todo lo demás.
